Section 02 • Identity & Isolation Flow

2. ระบบ Login, บัญชีเริ่มต้น, Onboarding แรกเข้า และ Pre-Hydration

บัญชีผู้ใช้งานเริ่มต้นที่ Seed เข้าสู่ระบบ (5 บัญชี)

Username Password เริ่มต้น Role ขอบเขตข้อมูล (Tenant)
admin admin321 admin จัดการทุก User + ดู/เปรียบเทียบทุกโรงงาน
ms-ssd msssd factory คลังโรงงาน MS-SSD (แยก 100%)
ms-kkd mskkd factory คลังโรงงาน MS-KKD (แยก 100%)
ms-amd msamd factory คลังโรงงาน MS-AMD (แยก 100%)
ms-ttd msttd factory คลังโรงงาน MS-TTD (แยก 100%)

รหัสผ่านทั้งหมดถูก Hash ด้วย 64-Round Salted SHA-256 ไม่เก็บ Plaintext ลงใน Cloud Document Store และทุก User มีปุ่ม เปลี่ยนรหัสผ่านด้วยตนเอง บน Navbar และหน้าโปรไฟล์มือถือ

ลำดับการทำงานตั้งแต่เปิดหน้าเว็บจนซิงค์ข้อมูล

1
Pre-Hydration ใน <head> (Synchronous): ก่อนสคริปต์ของหน้าเว็บจะทำงาน preHydrateBeforeBodyScripts() ตรวจ Session ปัจจุบัน ถ้ายังไม่ Login จะล้าง working localStorage; ถ้า Login แล้วจะคัดลอกค่าจาก stockms_tenant::{factoryId}::* ลง working keys ทันที
2
Authentication Gate: ล็อกหน้าจอหลักด้วยคลาส .stockms-locked (Blur + Disable) เมื่อผู้ใช้กรอก User/Pass ระบบพิสูจน์ตัวตนกับ Cloud Auth Engine (Credential เวอร์ชันล่าสุด + Secondary Fallback Token) และเทียบ Salted SHA-256 กับคอลเลกชัน /users/{username}
3
First-Time Onboarding (โรงงานใหม่): หากโรงงานที่เข้ามามี initialized === false ระบบจะเด้งหน้าต่างบังคับเลือก: (ก) นำเข้าไฟล์ Backup JSON (พร้อมแปลงชื่ออาคารเก่า B_70_Large/B_70/B_40 และโหลด QC Limits) หรือ (ข) เริ่มต้นฐานข้อมูลใหม่ ด้วยถังมาตรฐานแล้วซิงค์ขึ้น Cloud ทันที
4
Two-Way Real-Time Sync: ทุกการเรียก saveData() จะตั้ง Debounce 450ms อัปโหลด Document + Chunk ละ 350 รายการขึ้นฐานข้อมูลกลาง พร้อมเปิด Real-Time Listener รับอัปเดตจากเครื่องอื่นอัตโนมัติ (กรอง Timestamp > 1.5s และ factoryId บน BroadcastChannel)
Section 03 • Cloud Data Model & RBAC

3. โครงสร้างฐานข้อมูลกลาง & กฎความปลอดภัย (Cloud Security Rules)

/users/{username} 13 Allowed Fields Strictly

Doc ID ต้องตรงกับ Regex ^[a-z0-9][a-z0-9_-]{1,31}$ (ยาว 2–32 ตัวอักษร)

Required (9): username, displayName, role ('admin'|'factory'), passwordHash, salt, active (bool), createdAt, updatedAt, createdBy
Optional (4): authUid, authEmail, authVersion (int 1..100000), passwordChangedByUserAt
Rule: Non-admin ห้ามแก้ role, username, active; บัญชี admin หลักต้องมี role='admin' & active=true เสมอ
/factories/{username} 14 Allowed Fields Strictly

สร้างได้เมื่อมี /users/{username} อยู่แล้ว (exists || existsAfter) และอ่าน/เขียนได้เฉพาะเจ้าของหรือ Admin

Required (5): username, factoryName (<=120), initialized (bool), updatedAt, updatedBy
Optional (9): summary (<=60 keys), tankConfig (<=1000), activeTanks (<=500 list / 50 map), planningData (<=100), customTanks (<=1000), customBuildings (<=100), globalSettings (<=50), tankSettingsHistory (<=5000), customQCLimits (<=200)
/factories/{username}/chunks/chunk_{i} & snap_* 350 Tx / Chunk
Fields (3): chunkIndex (int 0..10000), transactions (list <= 5000 items), updatedAt
Client Policy: แบ่งชุดละ TX_CHUNK_SIZE = 350 รายการ และลบเฉพาะ chunk_* ส่วนเกิน (idx >= chunkCount) ส่วน snap_{logId}_b/a_{i} ใช้เก็บ Snapshot สำหรับ Rollback โดยถูกกรองออกจากการโหลดคลังปัจจุบัน
/auditLogs/{logId} Append-Only Immutable
Fields: actor (req), action (req), timestamp (req), target (opt), details (opt <=2000 chars or 30 keys)
Rule & Actions: allow update, delete: if false; บันทึกเหตุการณ์ Auth/Admin (LOGIN, LOGOUT, PASSWORD_CHANGE_SELF, ADMIN_CREATE_USER, ADMIN_RESET_PASSWORD, ADMIN_ROLLBACK), Data Onboarding (FIRST_TIME_IMPORT, FIRST_TIME_FRESH_START), Transactions (TX_RECEIVE_IN, TX_TRANSFER, TX_BLEND, TX_OUT, TX_EDIT, TX_DELETE, TX_RECONCILE) และ Settings พร้อมสถานะ before/after และปุ่ม Rollback แบบ Real-Time
การซิงค์ Key ภายในเครื่อง (9 Isolated LocalStorage Keys): liquor_transactions, tank_config, active_tanks, planning_data, custom_tanks, custom_buildings, global_settings, tank_settings_history, custom_qc_limits ทุก Key ถูกเก็บแยกภายใต้ prefix stockms_tenant::{username}::* พร้อม metadata __meta และสลับค่ามายัง working keys เมื่อ Admin สลับดูคลังโรงงานอื่นหรือเมื่อผู้ใช้เปลี่ยนบัญชี
Section 04 • Admin Operations & Decision Engine

4. สิทธิ์ของ Admin, การจัดการ User และการวิเคราะห์เปรียบเทียบทุกโรงงาน

เพิ่ม User & ตั้งรหัสผ่านใหม่

Admin สร้างบัญชีโรงงาน/Admin ใหม่ หรือกดรีเซ็ตรหัสผ่านให้ User ใดก็ได้โดยไม่หลุดจาก Session Admin ด้วยเทคนิค Secondary Auth Session พร้อมเพิ่มค่า authVersion (.v2, .v3, ...) และสร้างเอกสารเริ่มต้นใน /factories/{username} ให้อัตโนมัติ

สลับดู/บริหารคลังรายโรงงาน

ผ่าน Dropdown บน Navbar (navAdminFactorySelect) และแถบ Admin บนมือถือ (kmAdminFactorySelect) ระบบจะสั่ง saveFactoryToCloudNow() ของโรงงานเดิมก่อนล้าง working storage แล้ว Activate คลังปลายทางทั้งหน้า index.html และ dashboard.html

เปรียบเทียบทุกโรงงาน & กราฟ

รวบรวมสรุปจากทุกบัญชี role !== 'admin' คำนวณสต็อกรวม ความจุ %การใช้พื้นที่ แยกสุรา 70° vs 40°/35°/30°/28° อัตรา QC ผ่าน ยอดรับ-จ่าย 30 วัน แสดงตารางและกราฟแท่งเปรียบเทียบ (Chart.js) พร้อมปุ่มคลิกเข้าคลังโรงงานนั้นทันที

Real-Time Activity Logs & ย้อนข้อมูล (Rollback)

ติดตามการใช้งานผู้ใช้ทุกโรงงานแบบ Real-Time ผ่าน Cloud Listener ร่วมกับ BroadcastChannel('blending_stock_sync') และ storage event แจ้งเตือน Admin ทันที (Badge #navAdminLogsBadge + Toast #stockmsRealtimeLogToast) เปิดดูรายละเอียดและเทียบ Snapshot ได้ที่ #adminAuditLogsModal (previewLogSnapshot) และสั่งย้อนข้อมูลผ่าน adminRollbackFactory() ได้ทั้งโหมด before (ยกเลิกรายการ) และ after (คืนค่า ณ จุดเวลา) พร้อมบันทึก Log ADMIN_ROLLBACK อัตโนมัติ

เกณฑ์การสร้างบทสรุปและคำแนะนำอัตโนมัติ (generateFactoryRecommendations)

เงื่อนไขที่ตรวจพบ ระดับความเสี่ยง คำแนะนำที่ระบบสร้างให้ผู้บริหาร
!analytics.initialized watch (ติดตาม) แจ้งเตือนให้โรงงาน Login เพื่อ Import ไฟล์ Backup JSON หรือกดเริ่มต้นใช้งานใหม่
utilizationPct >= 88% critical (เร่งด่วน) พื้นที่จัดเก็บใกล้เต็ม — ควรเร่งจ่ายบรรจุหรือกระจายสุราเข้าถังว่าง/โรงงานเครือข่าย
utilizationPct < 20% && txCount > 0 watch (ติดตาม) ปริมาณสต็อกคงคลังค่อนข้างต่ำ — แนะนำตรวจสอบแผนรับกลั่นล่วงหน้า
(ready70 / v70) * 100 < 25% หรือ v70 == 0 watch (ติดตาม) สัดส่วนสุรา 70° ที่บ่มครบ 14 วันพร้อมปรุงต่ำ — ควรชะลอการเบิกเกินกำลังบ่ม / บันทึกยอดยกมา
qcIssues > 0 critical (เร่งด่วน) ระบุจำนวนรายการที่ไม่ผ่านเกณฑ์ QC และ % อัตราผ่าน — แนะนำตรวจสอบก่อนปล่อยบรรจุ
daysLeft70 !== null && daysLeft70 < 14 critical (เร่งด่วน) สต็อก 70° คงเหลือใช้ได้ต่ำกว่าเกณฑ์ Safety Stock 14 วันตามแผนใช้รายเดือน
Section 05 • Business Rules & Operational Constraints

5. กฎเกณฑ์ทางธุรกิจ (Business Rules) และข้อจำกัดของระบบ (Constraints)

กฎการคำนวณคลังสุรา (Inventory & FIFO Logic)

  • เกณฑ์อายุบ่มมาตรฐาน (Maturation Threshold): สุราดีกรีสูง (High / 70°) ต้องบ่มอย่างน้อย 14 วัน; สุราปรุงพร้อมบรรจุ (40° / 35° / 30° / 28°) ต้องพักอย่างน้อย 7 วัน
  • ระบบชั้นข้อมูล FIFO (First-In First-Out): รายการ IN / INITIAL_IN / TRANSFER_IN / BLEND_IN จะสร้าง Layer เรียงตาม date และ id เมื่อมีการเบิก/โอน/จ่าย (OUT) ระบบจะตัดยอดจาก Layer เก่าสุดก่อนเสมอ พร้อมถ่ายทอด sourceLayers และ targetDegree ไปยังถังปลายทาง
  • ข้อยกเว้นถังปรุงสุรา (Blending Tanks): ถังที่ชื่อขึ้นต้น/มีคำว่า ถังปรุงสุรา 1, ถังปรุงสุรา 2 (ความจุ 50,000 L ใน Building_110) เป็นถังพักผสมชั่วคราว ไม่ถูกนับรวมในความจุหรือยอดคงคลังสุราสำเร็จรูป เพื่อป้องกันการนับซ้ำ (Double Counting)
  • สถานะถัง bonded และ repair: ถังติดทัณฑ์บน (bonded) ถูกหักออกทั้งจากยอดคงคลังใช้งานและความจุคลังรวม; ถังซ่อมบำรุง (repair) ถูกหักออกจากความจุที่ใช้งานได้จริง
  • ความจุรายดีกรี & ประวัติถัง: อ้างอิงจาก globalSettings (cap70, cap40, cap35, cap30, cap28) ก่อน หากเป็น 0 จึง Fallback ไปคำนวณจาก TANK_DEFINITIONS ที่เปิดใช้งาน และใช้ tankSettingsHistory สำหรับรายงานย้อนหลัง

ข้อจำกัดและเงื่อนไขทางเทคนิค (System Constraints)

  • Cloud Auth Password Policy (ขั้นต่ำ 6 ตัวอักษร): รหัสผ่านเริ่มต้นของโรงงาน 4 แห่ง (เช่น msssd) ยาว 5 ตัวอักษรจึงแก้ด้วยฟังก์ชันแปลง Credential แบบ Deterministic (StkMS# + SHA-256) ก่อนส่งเข้า Auth Engine
  • โควตาขนาด Document 1 MiB ต่อเอกสาร: คลังที่มีธุรกรรมหลักพันรายการอาจเกิน 1 MiB จึงแก้โดยแยกธุรกรรมลง Subcollection chunks/chunk_{i} ชุดละไม่เกิน 350 รายการ
  • ความเร็วและการทำงาน Offline: เปิด Persistent Local Cache แบบข้ามแท็บเพื่อให้ทำงานต่อได้เมื่ออินเทอร์เน็ตหลุด และซิงค์กลับ Cloud เมื่อต่อติด (scheduleCloudSync หน่วง 450ms)
  • การให้บริการไฟล์บน HTTP/HTTPS: เพื่อประสิทธิภาพสูงสุดของ IndexedDB Cache, BroadcastChannel และ Clipboard/Fullscreen แนะนำรันผ่าน Web Server (HTTPS/localhost) แทนการเปิดผ่าน file:// โดยตรง
  • ข้อควรระวังเรื่องรหัสผ่าน Client-Side & Admin Reset: การใช้งานโปรเจกต์ Static HTML ใช้ Secondary Auth Session ร่วมกับ authVersion (.vN) เมื่อ Admin รีเซ็ตรหัสผ่าน; โปรดเปิดใช้ Email/Password Sign-in และ Fallback Auth บน Cloud Console พร้อมบังคับใช้ Cloud Security Rules อย่างเคร่งครัด
